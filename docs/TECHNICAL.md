# Технический разбор

Документ описывает, как устроен мост и что именно пришлось выяснить по ходу работы. Все выводы
получены на живом устройстве и подтверждены дизассемблированием библиотек Dolby.

## 1. Почему публичные Dolby-моды не работают на новых устройствах

Библиотеки Dolby (`libswdap.so`, `libswgamedap.so`, `libswvqe.so`, `libdlbvol.so`) не экспортируют
ни классический C-API эффектов, ни AIDL-контракт. Они экспортируют символ `AELI` - структуру
`audio_effect_library_t` (версия 3.1):

```c
struct audio_effect_library_s {
    uint32_t tag;                 // 'AELT'
    uint32_t version;             // 0x30000
    const char *name;             // "Effect DAP Library"
    const char *implementor;
    int32_t (*create_effect)(const effect_uuid_t *uuid, int32_t sessionId,
                             int32_t ioId, effect_handle_t *handle);
    int32_t (*create_effect_3_1)(/* ... */);
    int32_t (*query_effects)(/* ... */);
    int32_t (*get_descriptor)(const effect_uuid_t *uuid, effect_descriptor_t *desc);
    int32_t (*destroy_effect)(effect_handle_t handle);
};
```

Кто и что ищет:

| Загрузчик | Что делает `dlsym` | Кто использует |
|---|---|---|
| `libeffects.so` (frameworks/av) | `"AELI"` | старые устройства, HIDL-эффекты, audioserver |
| AIDL effect HAL (`EffectFactory.cpp`) | `"createEffect"` / `"queryEffect"` / `"destroyEffect"` | Android 14+ |

AIDL-контракт выглядит так (C++-подписи, не C):

```cpp
binder_exception_t createEffect(const AudioUuid* uuid, std::shared_ptr<IEffect>* instance);
binder_exception_t queryEffect (const AudioUuid* uuid, Descriptor* descriptor);
binder_exception_t destroyEffect(const std::shared_ptr<IEffect>& instance);
```

Библиотеки Dolby так не умеют. Готовой AIDL-сборки библиотек Dolby не существует: проверены три
независимые сборки из разных прошивок (Sony Xperia 5 V, Poco F4, Nothing Phone), во всех только `AELI`.

Диагностика на нашем устройстве (Realme GT 7T, Android 16):

- эффект-сервис MTK (`android.hardware.audio.effect.aidl-impl-mediatek.so`) не содержит ни строк
  `AELI`, ни `libeffects` - это чистый AIDL-реализация;
- старый `/vendor/lib64/libeffects.so` существует, но его никто не линкует (кроме мёртвого
  `libeffectproxy.so`);
- сервис `hwservicemanager` (нужен для HIDL-сервиса параметров Dolby) в состоянии `stopped`.

Итог: единственный работающий путь - свой мост.

## 2. Мост: как он устроен

Мост `libdolbyaidlshim.so` - это обычная AIDL-библиотека эффекта, которая внутри загружает
`libswdap.so` через `dlopen` и работает с ней через `AELI`.

Что приходится реализовать самому:

1. **Контракт AIDL.** Класс `DapEffect : public BnEffect` с методами `open`, `close`, `command`,
   `setParameter`, `getParameter`, `reopen`, `getState`, `getDescriptor`.
2. **Обмен аудио через общую память (FMQ).** Система отдаёт три очереди: статус, входные данные,
   выходные данные. Схема работы: система записывает буфер во входную очередь и будит эффект битом
   события, эффект обрабатывает, пишет результат в выходную очередь, пишет статус и будит систему
   битом `FMQ_NOT_EMPTY`.
3. **Синхронизацию без системного `EventFlag`.** Штатный `android::hardware::EventFlag` из `libfmq`
   не грузится в процессе HAL: системная сборка собрана с `std::__1`, а NDK даёт `std::__ndk1`,
   поэтому символ `createEventFlag(std::__ndk1::atomic<unsigned>*, ...)` не находится. Решение -
   своя реализация на фьютексах, повторяющая логику `system/libfmq/EventFlag.cpp`:
   `FUTEX_WAIT_BITSET` и `FUTEX_WAKE_BITSET` плюс атомарные операции над словом событий.
4. **Локальные заглушки** для трёх служебных функций AOSP (`android::hardware::details::logError`,
   `check`, `errorWriteLog`), у которых в системной сборке те же проблемы с ABI строк.

Используемые биты событий (проверено по заголовкам AOSP):

```
FMQ_NOT_FULL           = 0x1      (служебный бит очереди)
FMQ_NOT_EMPTY          = 0x2      (будим систему этим битом)
kEventFlagDataMqUpdate = 0x1 << 10
kEventFlagDataMqNotEmpty = 0x1 << 11   (система будит нас этим битом)
```

## 3. Особенности протокола Dolby, без которых ничего не работает

Эти детали выяснены дизассемблированием и проверены на устройстве. Каждая из них в отдельности
приводила к отказу или падению.

**1. Настоящий UUID эффекта берётся из библиотеки.** Публичные конфиги модов используют UUID
`9d4921da-8225-4f29-aefa-39537a04bcaa`, но библиотека ожидает свой, отличный:

```
9d4921da-8225-4f29-faae-39537a04bc06
```

Проверка: `create_effect` с публичным UUID возвращает `-2` (`ENOENT`), с библиотечным - `0`.
UUID берётся из символа `_ZN5dolby9DlbEffect11kDescriptorE`.

**2. Структура аудио-буфера у Dolby отличается от системной.** В AOSP первым полем идёт указатель на
данные, у Dolby - счётчик кадров:

```c
// AOSP
struct audio_buffer_s { union { void *raw; float *f32; } audio; uint32_t frameCount; };
// Dolby (проверено по коду AudioBufferProvider::set)
struct audio_buffer_s { uint32_t frameCount; uint32_t _pad; union { void *raw; float *f32; } audio; };
```

С системным порядком движок читает счётчик как указатель и падает на адресе `0x800`.

**3. Формат сэмплов нумеруется иначе, чем в заголовках Android.** `SET_CONFIG` принимается только с
`format = 5` (`AUDIO_FORMAT_PCM_FLOAT`), при `4` возвращается `-22` (`EINVAL`), а обработка потом
отвечает `-38` (`ENOSYS`, "не сконфигурирован").

**4. Каналы задаются индексной маской**, а не маской каналов: стерео это `0x3` (не `0xC` и не
количество каналов `2`), 5.1 - `0x3F`, 7.1 - `0x63F`.

**5. `EFFECT_CMD_INIT` обязателен.** Без него внутренние структуры движка остаются нулевыми, и первый
же буфер приводит к падению в `DapCrossfadeProcess::process`. Команда отправляется после
`SET_CONFIG`.

**6. `SET_DEVICE` в момент открытия эффекта роняет движок.** Устройство вывода сообщается только
тогда, когда система сама присылает описание устройства.

## 4. Параметры Dolby: как управлять звуком без сервиса DMS

Штатно параметры (эквалайзер, громкость, виртуализация) приходят от сервиса Dolby
(`vendor.dolby.hardware.dms@2.0-service`), который читает профили из XML. На AIDL-аудио этот сервис
не запускается, поэтому параметры передаются движку напрямую, через команду эффекта.

**Формат посылки.** `EFFECT_CMD_SET_PARAM` со структурой `effect_param_t`, внутри которой лежит блоб
следующего вида:

```
effect_param_t {
    uint32_t status;      // 0
    uint32_t psize;       // 4   (должно быть ровно 4)
    uint32_t vsize;       // размер блоба
    uint32_t paramId;     // 0 = EFFECT_PARAM_SET_VALUES
    uint8_t  blob[vsize];
}

blob {
    uint32_t activeDevice;               // аудио-устройство (см. ниже)
    uint32_t numParams;                  // сколько параметров внутри
    struct {
        uint32_t deviceId;               // устройство для этого параметра
        uint32_t paramId;                // код параметра (четыре символа)
        uint32_t numValues;              // сколько значений
        int32_t  values[numValues];
    } params[];
}
```

**Условие, из-за которого параметры "принимаются, но не действуют".** В
`DapEffectContext::setParamValues` движку передаётся каждый параметр, а затем вызывается коммит
(виртуальный вызов, слот +0x60). Коммит выполняется **только если `activeDevice != 0`**, это видно в
дизассемблере как проверка `CBZ` по полю-смещению:

```asm
LDR   W1, [SP,#var_30]      ; activeDevice из блоба
CBZ   W1, loc_skip_commit   ; ноль -> коммита нет, параметры не применяются
LDR   X8, [X0]
LDR   X8, [X8,#0x60]        ; виртуальный метод commit
BLR   X8
```

Пока в посылке стояли нули, движок отвечал "успех" (`status=0`) и не менял в обработке ничего: звук
проходил насквозь. С реальным устройством (например, `0x2` для динамика, `0x8` для наушников)
параметры начинают применяться.

**Дополнительные условия:**

- В конструкторе контекста по смещению `+205` выставляется флаг со значением `1`, который отключает
  фильтр "content processing" в `setParamValues`. Если бы он был нулевым, часть параметров
  (диалоги, эквалайзер, выравниватель) молча отбрасывалась бы.
- Сам Dolby при создании движка вызывает `init()`, который обнуляет 23 флага-включения: `deon`,
  `dvle`, `ieon`, `dvme`, `dom`, `msce`, `miee`, `mdle`, `mdee`, `mave`, `mvbe`, `ngon`, `rvse`,
  `ceon`, `geon`, `aoon`, `beon`, `vbm`, `bexe`, `rsse`, `hpon`, `bmde`, `arde`. То есть по умолчанию
  обработка полностью прозрачная, и её нужно включать явно.
- Значения для профиля берутся из эталонного файла настроек Dolby (`dax-default.xml`): например,
  `bass-enhancer-boost = 192`, `volmax-boost = 56` для динамика и `32` для наушников,
  `volume-leveler-in-target = -256`, конфигурация виртуализатора `35,32568,11164,5090,0,3,3,3`.

Полная таблица найденных кодов - в [PARAMS.md](PARAMS.md).

## 5. Как проверялась обработка (и почему наивная проверка врёт)

Dolby обрабатывает звук **прямо во входном буфере**: в `DapEffectContext::process` движок получает
один и тот же буфер как вход и как выход, а затем результат копируется в выходной буфер системы.
Поэтому сравнение "вход против выхода" внутри моста всегда показывает нулевую разницу - сравнивается
уже обработанный буфер с его же копией.

Корректный замер: снять копию входного буфера до вызова обработки и сравнить её с результатом. В
мосте для этого есть счётчик отличающихся сэмплов, он печатается в лог:

```
DSP: rms_in=0.002720 rms_out=0.010185 gain=+11.47dB maxdiff=0.036537 diff=4096/4096
```

`diff=4096/4096` означает, что изменился весь буфер, `gain` показывает работу выравнивателя
громкости, `[bypass]` - что обработка выключена и включён прозрачный режим.

## 6. Управление из приложения

Приложение не требует root: оно пишет два файла в каталог `/data/vendor/dolby` (каталог доступен на
запись), а мост читает их раз в секунду:

- `dolby_bypass` со строкой `1` - обработка выключена (прозрачный режим);
- `dolby_params.txt` - параметры строками вида `beon 1`, `beb 160`, `dea 4`.

Мост применяет профиль при старте каждого аудиопотока, а затем следит за изменениями файла и
переприменяет параметры на лету. Если файла нет, используется встроенный профиль Dolby.

## 7. Ограничения подхода

- Нужны библиотеки Dolby под arm64 (проприетарные, в репозиторий не входят).
- Нужен AIDL-аудио-стек (Android 14 и выше в такой конфигурации).
- Root нужен для развёртывания: мост регистрируется в системных конфигах и подменяет каталоги
  библиотек через bind-монтирование. Постоянных изменений в системе нет.
- Сервис Dolby (`DMS`) не используется, поэтому фирменные профили производителя недоступны: набор
  параметров задаётся вручную (профили в приложении повторяют логику эталонных профилей Dolby).
